Kubernetes Manifest Security Checklist: 13 Things to Check Before You Deploy

Security · 8 min read

Most Kubernetes security incidents don't start with a zero-day. They start with a manifest that got merged without anyone noticing it was missing a securityContext, or that a container image tag was left as latest. None of these are exotic mistakes — they're defaults, and Kubernetes' defaults are permissive by design because the API has to support every workload from a stateless web app to a CNI plugin that genuinely needs host networking.

This is the checklist Cubzi runs automatically on every manifest — 13 rules split into critical, warning, and informational severity. Here's what each one actually protects against.

Critical: fix these before you deploy

1. Container may run as root

If neither the pod nor the container sets securityContext.runAsNonRoot: true, the container runs as whatever user the image's Dockerfile specifies — which, for the vast majority of public images, is root. A process running as root inside a container that has any host mount, capability, or kernel exploit available to it has a much shorter path to breaking out than the same process running as an unprivileged UID.

securityContext:
  runAsNonRoot: true
  runAsUser: 1000

2. Privileged container

securityContext.privileged: true disables essentially every container isolation mechanism Linux provides — the container gets full access to host devices and can load kernel modules. It's occasionally legitimate (some CNI and storage daemons need it), but it should never be the default and should never appear in an application workload's manifest.

3. Secret hardcoded in an env var

A database password or API token set directly under env: value: ends up in the pod spec, which is readable by anyone with get pods RBAC access, and it's stored in plaintext in etcd unless encryption-at-rest is configured. Reference a Secret via valueFrom.secretKeyRef instead — the value never appears in the manifest, and access can be scoped independently.

4. hostNetwork / hostPID / hostIPC enabled

These three fields all do the same kind of thing: they remove a Linux namespace boundary between the container and the host. hostNetwork means the container shares the node's network stack (no network isolation, and it can bind to any port on the node). hostPID and hostIPC expose the host's process table and IPC namespace. Unless you're writing a node-level monitoring agent, these should stay off.

Warning: fix these before you scale

5. Missing CPU/memory requests or limits

Without resources.requests, the scheduler has no idea how much CPU or memory your pod actually needs, which means it can't bin-pack nodes efficiently and can't protect your pod from being starved by a noisy neighbor. Without limits, a single pod with a memory leak can consume an entire node. This is also the field Cubzi's cost estimator reads — no requests means no cost estimate at all.

6. Missing liveness/readiness probes

Without a readinessProbe, Kubernetes sends traffic to a pod the moment its container starts, even if the application hasn't finished booting. Without a livenessProbe, a hung process that never crashes just sits there serving nothing, forever, because Kubernetes has no signal to restart it.

7. No PodDisruptionBudget for multi-replica workloads

Covered in depth in our PDB deep-dive — in short, without one, a routine node drain during a cluster upgrade can evict all replicas of a Deployment at once.

8. Image tag not pinned

An image reference with no tag (or the tag latest) means the exact code running in production can change on the next pod restart, with no corresponding commit or PR. Pin to a specific tag or, better, a digest.

9. No explicit replica count

Omitting spec.replicas defaults to 1 — a Deployment with no explicit count is a single point of failure that nobody decided on purpose.

10. No NetworkPolicy in the namespace

Covered in our NetworkPolicy explainer — the short version is that Kubernetes networking is allow-all between pods by default, cluster-wide, until a NetworkPolicy says otherwise.

Info: worth cleaning up

  • No team/environment/owner label — without a consistent label like team or env, cost and incident attribution across a cluster with many workloads becomes guesswork.
  • PVC with no storageClassName — relies on whatever the cluster's default StorageClass happens to be, which is often not what you'd choose deliberately.
  • No terminationGracePeriodSeconds — the default 30 seconds may be too short for a workload that needs to drain in-flight requests or finish a long write.
