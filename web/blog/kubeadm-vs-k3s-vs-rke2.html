kubeadm vs k3s vs RKE2: Choosing a Kubernetes Distribution for On-Premises

DevOps · 8 min read

Every managed cloud offering (EKS, GKE, AKS) hides the control plane from you. On-premises, you're the one standing it up — and the tool you pick for that changes how much operational work you sign up for afterward. The three real contenders are kubeadm, k3s, and RKE2. They solve overlapping problems in different ways.

kubeadm: the upstream building block

kubeadm is the official Kubernetes bootstrapping tool — it initializes a control plane and joins worker nodes using the same components a cloud provider's managed control plane runs. It gives you the closest thing to "vanilla upstream Kubernetes," which matters if you need to match a specific cloud cluster's behavior exactly, or you want full control over every component's version.

The tradeoff is that kubeadm hands you a working control plane and stops there — you still choose and install your own CNI, ingress controller, and storage driver, and HA (stacked or external etcd) is a manual, multi-step process you're responsible for getting right.

Reach for kubeadm when

  • You need version parity with a specific upstream Kubernetes release for compliance or testing reasons.
  • Your team already has the operational depth to manage etcd, CNI, and upgrades by hand.
  • You're building your own opinionated platform on top and don't want a distribution's defaults in the way.

k3s: minimal footprint, edge-first

k3s (from Rancher/SUSE) is a single ~70MB binary that bundles the control plane, a lightweight CNI (flannel by default), a local storage provisioner, and an ingress controller (Traefik) — and swaps etcd for SQLite by default, though it supports etcd or an external datastore for HA. It was built for edge and resource-constrained environments, and it shows: a single-node k3s cluster runs comfortably on 512MB of RAM.

The bundled defaults are also the main caveat — swapping out Traefik for a different ingress controller or flannel for Cilium means first disabling the bundled component, which is an extra step vanilla kubeadm doesn't require.

Reach for k3s when

  • You're deploying to edge locations, IoT hardware, or resource-constrained VMs.
  • You want a cluster running in minutes with sane defaults, and you're fine with (or want) the bundled components.
  • You're running dev/staging clusters and want the lightest possible footprint.

RKE2: k3s's security-hardened, enterprise-facing sibling

RKE2 (also from Rancher/SUSE, the successor to RKE) is built from the same lineage as k3s but targets production/regulated environments instead of the edge: it defaults to etcd (not SQLite), ships CIS Kubernetes Benchmark-hardened defaults out of the box, and integrates cleanly with Rancher for multi-cluster management. It's heavier than k3s but lighter than a full manual kubeadm setup with all the operational tooling built around it.

Reach for RKE2 when

  • You need CIS-hardened defaults and FIPS-compliant builds for a regulated industry.
  • You're running production on-premises workloads and want etcd HA without assembling it yourself.
  • You're managing multiple on-premises clusters and want Rancher's fleet management on top.
