Kubernetes Cost Estimation: AWS vs GCP vs Azure Pricing Compared

Cost · 6 min read

The same Kubernetes manifest, applied to a cluster on AWS, GCP, or Azure, will cost a different amount every time — not because Kubernetes behaves differently, but because the underlying compute it's scheduled onto is priced differently, and none of the three clouds sells "a vCPU" and "a GB of memory" as separately priced line items you can look up directly.

The core problem: no cloud sells resources à la carte

Every major cloud prices compute as fixed instance types — an AWS m6i.large bundles 2 vCPU and 8 GiB memory for one hourly rate; you can't buy "1 vCPU" and "4 GiB" separately and get a meaningfully different price. That's a reasonable pricing model for buying VMs, but Kubernetes workloads request CPU and memory independently and in whatever ratio the application actually needs, which rarely matches an instance type's ratio exactly.

How a per-resource rate gets derived

The practical approach is to solve for an implied per-vCPU and per-GiB rate using two instance types with meaningfully different vCPU:memory ratios — a compute-optimized type and a memory-optimized type at the same vCPU count give you two equations and two unknowns. Cross-checking the result against a third, balanced instance type (like AWS's general-purpose m family) confirms whether the derived rate is a reasonable approximation — typically within a few percent for on-demand list prices.

This is, explicitly, an approximation — it assumes a linear relationship between resource and price that real instance-type pricing only roughly follows, and it uses list (on-demand) prices, not the reserved-instance, savings-plan, or spot pricing many production clusters actually run on. It's the right tool for comparing "should this be 500m or 1000m CPU" before a merge, not for reconciling an actual invoice.

Why the three clouds still come out different

Even with a consistent estimation methodology, AWS, GCP, and Azure list prices for comparable compute genuinely differ — sometimes by double-digit percentages depending on region and instance family — because each cloud's pricing reflects its own hardware generations, discounting structure, and regional capacity. A workload estimated at $40–50/month on one cloud might come out at $35–45/month on another, and that gap is real, not a modeling artifact — it's exactly the kind of number worth seeing before committing to a cloud, or before assuming a lift-and-shift migration is cost-neutral.

Using this in practice

The useful workflow isn't "find the cheapest cloud" — for most teams, the cloud is already chosen for reasons far beyond compute pricing. It's catching regressions early: a PR that bumps memory requests from 512Mi to 2Gi across 5 replicas should show up as a visible cost delta in review, on whichever cloud you're actually running, before it's merged — not as a line item you notice on next month's invoice.
