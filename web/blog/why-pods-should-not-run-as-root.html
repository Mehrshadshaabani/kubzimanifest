Why Your Pods Shouldn't Run as Root (and How to Fix It)

Security · 5 min read

Ask why a container shouldn't run as root and the honest answer is: it depends on what else goes wrong. Running as root inside a container isn't itself a breach — it's the thing that turns an unrelated bug into one. A path traversal in your app, a compromised dependency, a misconfigured volume mount: any of these is far more dangerous if the process that hits it is root.

What root inside a container can actually do

By default, Linux containers share the host kernel. Root inside a container isn't identical to root on the host — namespaces and capabilities narrow what it can do — but it still starts from a much larger set of privileges than an unprivileged UID: writing to any file owned by root inside the container (including ones mounted from a ConfigMap or Secret with restrictive permissions meant for a specific user), binding to privileged ports, and, critically, a much shorter list of additional missteps needed to escalate to the host if anything else is also misconfigured — a writable hostPath mount, a mounted Docker socket, an overly broad capability set.

The fix is three lines

Kubernetes lets you set this at the pod level (applies to every container) or per-container:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000

runAsNonRoot: true is actually the important one from a policy standpoint — it tells the kubelet to refuse to start the container at all if the resulting user turns out to be UID 0, which catches the case where an image's Dockerfile changes later and silently starts running as root again. runAsUser pins the exact UID.

What if the image only works as root?

Some base images genuinely assume root — they chown files at startup, bind to port 80 directly, or write to directories only root can write to. The fix belongs in the image, not the deployment: create a non-root user in the Dockerfile, chown the directories it needs at build time, and use USER 1000 before the entrypoint. It's extra work once, per image, that then applies to every deployment of that image forever.

Related: privileged and capabilities

runAsNonRoot addresses the user the process runs as. It's a separate (and larger) problem if securityContext.privileged: true is also set, since that grants the container access to host devices regardless of which UID is running inside it — see the full checklist for that one.
