Common Kubernetes Misconfigurations That Lead to Security Incidents

Security · 7 min read

Publicly documented Kubernetes security incidents tend to follow a small number of recurring patterns. None of them require a novel exploit — they're almost always a chain of ordinary-looking misconfigurations that, combined, add up to a compromise. Here are the patterns that show up most often, and the specific manifest fields behind each one.

Pattern 1: an exposed dashboard or API with no authentication

Several well-known cluster compromises started with a Kubernetes Dashboard or a debugging tool exposed to the public internet with anonymous access enabled, often via a LoadBalancer Service or an Ingress with no authentication middleware in front of it. This isn't a manifest-linting problem in the strict sense — it's an architecture decision — but it's worth naming as the single most common root cause in incident writeups, and it's a reminder to audit every Service of type LoadBalancer and every public Ingress in a cluster for what's actually behind it.

Pattern 2: a compromised container that was root and privileged

The second-most-common pattern: a vulnerability in an application (often a deserialization bug, an SSRF, or a vulnerable dependency) gives an attacker code execution inside a container — and that container turns out to be running as root, sometimes with privileged: true set for reasons nobody could later explain. From there, escaping to the host or to other pods on the node is a matter of degree, not a separate exploit. This is exactly what runAsNonRoot and avoiding privileged: true defend against — not preventing the initial compromise, but capping how far it can spread.

Pattern 3: a hardcoded credential in a manifest that reached a public or overly-accessible repo

Secrets committed directly into manifest YAML — a database password in a plain env: value:, an API key baked into a ConfigMap — have leaked through public GitHub repos, CI logs, and even Kubernetes' own audit logs. The fix (referencing a Secret via secretKeyRef instead of a literal value) doesn't just hide the value from casual viewing — it means the credential's blast radius is scoped by RBAC on the Secret object, rather than by however wide the manifest itself has been shared.

Pattern 4: unrestricted lateral movement after an initial foothold

Once an attacker has a foothold in one pod, the absence of a NetworkPolicy means they can typically reach every other pod in the cluster directly — including internal admin tools, databases, and metadata services that were never meant to be reachable from a public-facing frontend's network position. A default-deny NetworkPolicy baseline turns a single compromised pod into a contained incident instead of a cluster-wide one.

What these have in common

Every one of these is checkable from the manifest alone, before anything is deployed — none of them require a running cluster or runtime telemetry to catch. That's the specific gap automated manifest linting is meant to close: not replacing runtime security tooling, but catching the misconfigurations that make a runtime incident far worse than it needed to be, at the point where fixing them costs nothing more than a one-line YAML change.
