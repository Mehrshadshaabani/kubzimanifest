From Free Tier to Production: A Guide to Kubernetes Cost Optimization

Cost · 7 min read

Kubernetes cost optimization advice tends to jump straight to cluster-level tooling — autoscalers, spot instance strategies, bin-packing schedulers. All genuinely useful, and all downstream of a much simpler starting point: most Kubernetes overspend traces back to individual manifests requesting more than they need, or being sized once early on and never revisited.

Start with requests, not infrastructure

Before touching cluster autoscaling policy, look at what your existing workloads actually request versus what they use. It's extremely common to find services requesting 1 full CPU "to be safe" that use a tenth of that in practice — every one of those is directly inflating both the node count the cluster needs and the estimated monthly cost of that workload. Right-sizing requests based on observed usage (with reasonable headroom, not a guess) is almost always the highest-leverage first move.

Replica count is a multiplier, not a fixed cost

A workload's cost scales linearly with replica count, which makes replica count one of the more consequential decisions in a manifest — and one that's often set once, early, and never reconsidered as traffic patterns become clearer. A service that genuinely needs 5 replicas at peak but runs at 5 replicas around the clock is paying peak price permanently; a HorizontalPodAutoscaler that scales between a lower floor and that same ceiling captures the same peak capacity without the constant cost.

Storage adds up quietly

PersistentVolumeClaims are easy to forget about because they don't show up in the same "is this pod using too much CPU" conversations — but storage cost accrues independent of whether the workload using it is even running, and orphaned PVCs (left behind after a Deployment is deleted, if the PVC wasn't part of the same cleanup) are a common source of cost that nobody's actively watching.

Catch drift before it compounds

The pattern behind most Kubernetes cost surprises isn't a single bad decision — it's a series of individually small ones (a memory bump here, an extra replica there) that never got reviewed with cost in view, because nothing surfaced the cost impact at the time the change was made. This is the specific gap a pre-deploy cost estimate closes: showing the monthly delta in the same pull request that changes the resource requests, so "this PR adds roughly $12/month" is something a reviewer sees, not something finance notices two months later.

A reasonable cadence

You don't need continuous cost monitoring to get most of the benefit. A quarterly pass — checking every workload's requests against actual usage, reviewing replica counts against real traffic, and auditing for orphaned PVCs — combined with cost estimation on every PR that changes resource fields, catches the overwhelming majority of avoidable Kubernetes spend without needing dedicated FinOps tooling.
