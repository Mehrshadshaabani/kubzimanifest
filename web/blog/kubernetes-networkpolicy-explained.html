NetworkPolicy 101: Why Your Namespace's Pod Traffic Might Be Wide Open

Security · 6 min read

Here's a fact that surprises a lot of people the first time they hear it: by default, any pod in a Kubernetes cluster can send traffic to any other pod in any namespace, on any port. There's no implicit isolation between namespaces, and there's no implicit isolation between an internal admin service and a public-facing web frontend, unless something has explicitly said otherwise.

Why Kubernetes defaults this way

Kubernetes networking is deliberately unopinionated at the base layer — the CNI plugin provides pod-to-pod connectivity, full stop, and policy enforcement is an opt-in layer on top (implemented by the CNI plugin, which is why NetworkPolicy support depends on which CNI you're running — Calico, Cilium, and most managed cluster CNIs support it; the default kubenet on some older setups doesn't). The result is a cluster that "just works" for connectivity out of the box, at the cost of having zero network segmentation until someone adds it.

What a NetworkPolicy actually does

A NetworkPolicy is a namespace-scoped object that selects a set of pods (via labels) and then defines allowed ingress and/or egress rules for them. The moment any NetworkPolicy selects a pod, that pod's traffic in the direction(s) covered by the policy switches from allow-all to deny-all-except-what's-listed. No policy at all means no restriction; one policy means only that policy's rules apply.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend-only
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 8080

This example says: pods labeled app: api only accept ingress traffic from pods labeled app: frontend, on port 8080. Everything else — traffic from other namespaces, other services in the same namespace, egress to arbitrary destinations — is untouched by this specific policy (egress stays open unless a separate policy addresses it too).

A practical starting point

Rather than trying to write precise policies for every service on day one, many teams start with a default-deny baseline per namespace and then add specific allow rules as needed:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes: [Ingress]

An empty podSelector matches every pod in the namespace; with no ingress rules listed, nothing is allowed in. From there, each service that legitimately needs to receive traffic gets its own explicit allow rule — which also has the side benefit of making your namespace's actual traffic topology visible in the manifests themselves, instead of implicit and undocumented.
