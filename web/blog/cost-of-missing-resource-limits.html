The Hidden Cost of Missing Resource Requests and Limits

Cost · 6 min read

Of all the fields a Kubernetes manifest can omit, resources.requests and resources.limits are the two most likely to be missing — and the two with the widest-reaching consequences, touching both reliability and cost in ways that aren't obvious until something goes wrong.

What requests and limits actually do

Requests are what the scheduler reserves. If a node has 4 vCPU free and your pod requests 500m, the scheduler subtracts that 500m from the node's available capacity for the purposes of placing other pods — whether or not your container actually uses that much. Limits are a hard ceiling enforced by the kernel: a container that exceeds its memory limit gets OOM-killed; one that exceeds its CPU limit gets throttled.

No requests: the scheduler is flying blind

A pod with no requests set is treated by the scheduler as needing essentially nothing, so it can be packed onto any node regardless of actual load. In practice this means a handful of "weightless" pods can end up co-located on the same node and then simultaneously spike, with no mechanism to have prevented it — the scheduler did exactly what it was told, which was nothing.

No limits: one pod can take down a node

Without a memory limit, a container with a leak (or just a legitimately larger-than-expected workload) can consume memory until the node itself runs out, at which point the kubelet starts evicting pods — not necessarily the offending one first. A limit turns "the whole node goes unstable" into "this one container gets OOM-killed and restarted," which is a much smaller blast radius.

The cost angle

This is also, mechanically, why a manifest with no requests set produces no cost estimate. Cost estimation works by reading what a workload has reserved and pricing that reservation against compute rates — there's nothing to price if nothing was declared. It's not a limitation of the estimator; it's a genuine reflection of the fact that an un-sized workload has an genuinely unknown cost until it's actually running and you're reading it off a bill after the fact, which is exactly the situation a pre-deploy check is meant to avoid.

A reasonable starting point

You don't need perfect numbers on day one. A common, defensible pattern: set requests close to typical observed usage (or a conservative estimate for a new service) and limits at roughly 1.5–2x requests for CPU, and equal to requests for memory (CPU throttling degrades gracefully; memory limits that are too tight cause hard OOM kills, so memory is the one worth being generous with).

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 256Mi
