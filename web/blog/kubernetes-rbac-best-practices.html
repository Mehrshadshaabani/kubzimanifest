Kubernetes RBAC Best Practices: Least Privilege Without the Pain

Security · 9 min read

Most clusters start with RBAC turned on and every ServiceAccount bound to cluster-admin "just to get it working" — and then that binding never gets revisited. It's the single most common finding in every cluster audit we run: not a missing NetworkPolicy, not an unpinned image tag, but a ServiceAccount that can delete any resource in any namespace when it only ever needed to read ConfigMaps in one.

RBAC in Kubernetes is genuinely simple once you separate the four objects it's built from. The complexity people run into is almost always a design problem, not an API problem.

The four objects, in one paragraph each

Role and ClusterRole: what's allowed

A Role defines a set of permissions (verbs like get, list, create, delete on resources like pods, secrets, deployments) scoped to a single namespace. A ClusterRole is the same idea but not bound to a namespace — it can be applied cluster-wide, or scoped to one namespace when referenced by a RoleBinding instead of a ClusterRoleBinding. Reach for ClusterRole only when the permission genuinely needs to span namespaces (node access, CRDs, PersistentVolumes) — not by default.

RoleBinding and ClusterRoleBinding: who gets it

A binding attaches a Role/ClusterRole to a subject — a User, Group, or ServiceAccount. This is the piece that most often gets left too broad: a ClusterRoleBinding to cluster-admin is the RBAC equivalent of running every container as root.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: billing
  name: configmap-reader
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: billing
  name: billing-app-configmap-reader
subjects:
  - kind: ServiceAccount
    name: billing-app
    namespace: billing
roleRef:
  kind: Role
  name: configmap-reader
  apiGroup: rbac.authorization.k8s.io

Where clusters actually go wrong

1. Every workload gets the default ServiceAccount

If a Pod spec doesn't set serviceAccountName, it runs as the namespace's default ServiceAccount — and if that ServiceAccount has any binding at all (even indirectly, via a broad ClusterRoleBinding), every unrelated workload in the namespace inherits it. Give every application its own ServiceAccount, scoped to exactly what it needs.

2. Wildcard verbs and resources

verbs: ["*"] or resources: ["*"] shows up constantly in Roles that were written once under deadline pressure and never trimmed. It's almost never actually required — list the specific verbs the workload calls.

3. Secrets access bundled with everything else

get on secrets is one of the highest-value permissions in the entire API — it's frequently how a compromised low-privilege pod becomes a cluster-wide incident, by reading a ServiceAccount token or a cloud credential out of a Secret it never needed to see. Put secrets permissions in their own Role, bound only to the specific ServiceAccounts that read that specific Secret.

4. cluster-admin bound to CI/CD

A CI/CD pipeline that deploys to one namespace doesn't need cluster-admin — it needs create/update/delete on Deployments, Services, and ConfigMaps in that one namespace. Scope the deploy-time ServiceAccount to exactly that.

A least-privilege pattern that scales

Rather than writing one Role per application from scratch, define a small number of reusable ClusterRoles (e.g. app-runtime: read ConfigMaps/Secrets in its own namespace, app-deployer: manage Deployments/Services in its own namespace) and bind them per-namespace with RoleBindings. New services get a ServiceAccount and two bindings, not a bespoke policy document.

Run kubectl auth can-i --list --as=system:serviceaccount:NAMESPACE:SERVICEACCOUNT against every ServiceAccount in a cluster before an audit — it prints exactly what that identity can do, and is usually the fastest way to find the one binding that's wider than everything else combined.
