How to Add Kubernetes Manifest Linting to Your CI/CD Pipeline

CI/CD · 5 min read

A linter that only runs when someone remembers to run it locally catches roughly nothing. The value of manifest linting compounds when it runs automatically on every pull request that touches Kubernetes YAML — visible to the reviewer, before merge, with no extra step for the author to remember.

What "in CI" actually buys you

Three things a local-only check can't give you: it runs the same way for every contributor regardless of what's installed on their machine, it's visible to reviewers directly in the PR instead of hidden in someone's terminal, and it can block a merge outright when something critical is found — turning a convention ("please set resource requests") into an actual gate.

Adding the Cubzi GitHub Action

Drop this into a workflow file (.github/workflows/lint-manifests.yml):

name: Lint Kubernetes manifests
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Mehrshadshaabani/kubzimanifest@v1
        with:
          path: ./manifests
          cloud: aws

This builds and runs the CLI against every manifest under ./manifests, posts (and updates, on subsequent pushes) a single PR comment with the full table report, and fails the job if any CRITICAL-severity finding is present — a hardcoded secret or a privileged container blocks the merge; a missing label just shows up as an informational note.

Authenticating so CI doesn't hit the anonymous rate limit

Every check runs against the hosted API, and anonymous requests share a per-IP rate limit — fine for occasional local use, but a busy CI runner can trip it under real usage. Generate an API key from the panel (Open the tool → API keys), store it as a repository secret, and pass it to the Action:

      - uses: Mehrshadshaabani/kubzimanifest@v1
        with:
          path: ./manifests
          cloud: aws
          api-key: ${{ secrets.CUBZI_API_KEY }}

Deciding what blocks a merge

The default behavior — fail only on CRITICAL — is a reasonable starting point: it catches root containers, privileged pods, hardcoded secrets, and host-namespace usage without blocking a merge over something like a missing label. Teams that want stricter gating can layer their own policy on top by parsing the Action's critical-count output, or by reading the full JSON report the CLI can also produce.

The same check that runs in CI is available as a paste-and-check web tool and a local CLI — so a developer can run the exact same rules before ever opening a PR, not just find out about a problem after pushing.
